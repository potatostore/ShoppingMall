## 2. 변경 상세 (문제 → 해결 → 택하지 않은 대안 → 검증)

### 2-1. 회원가입 role 서버 고정 (26046ab)
- 문제: `UserCreateDTO.signUpRole`을 그대로 저장 → `{"signUpRole":"ADMIN"}`으로 가입하면 ROLE_ADMIN 획득 (copilot-addendum 20261007 구현 기능 관련 문제점 1번)
- 해결: DTO 필드와 회원가입 화면의 Role 입력칸 삭제, `UserService`가 `RoleNames.USER`로 고정 저장. 클라이언트가 signUpRole을 보내도 Jackson이 무시함
- 택하지 않은 대안: 서버에서 "ADMIN이면 거부" 검증(허용 목록이 아니라 차단 목록이라 소문자·공백 등 우회 여지), role enum 전환(Phase 3 스키마 작업 때 결정하기로 한 사항)
- 검증: `UserServiceTest.userCreateTest`에 저장된 role이 USER인지 확인 추가
- ADMIN 계정은 DB 직접 생성 또는 Phase 4 seed로 만들어야 함

### 2-2. 이메일 중복 400 (0a92e2b)

- 해결: 가입·이메일 변경 전에 `existsByEmail` 확인 → `AlreadyExistException(USER_ALREADY_EXIST)` 400. 확인과 insert 사이에 동시 가입이 끼어드는 경우의 `DataIntegrityViolationException`도 같은 예외로 변환
- 택하지 않은 대안: `DataIntegrityViolationException` 전역 핸들러(어떤 제약 위반인지 구분 못 함)

### 2-14. 토큰 재발급 (0101a28)
- 해결
  1. POST /auth/reissue (공개): HttpOnly refreshToken 쿠키 → 서명·만료·type 검증 → Redis 값과 비교 → 새 access + refresh 발급, Redis 교체(rotation). 실패 시 401 INVALID_REFRESH_TOKEN(A001)
  2. 저장된 값과 다른 refresh token(이미 교체됐거나 다른 기기 로그인으로 덮어써진 토큰)은 401. 처음에는 재사용 감지로 저장된 토큰까지 지웠으나, 사용자당 토큰 1개 구조에선 기기 A의 재발급 시도가 기기 B의 정상 세션까지 끊어서 a11cfd7에서 제거 (멀티 디바이스 정책과 함께 Phase 5에서 결정)
  3. JWT에 type 클레임(access/refresh), refresh token에 jti. 필터는 refresh token을 인증에 쓰지 않고, 재발급은 access token을 거부
  4. 새 토큰은 토큰 클레임이 아니라 DB의 현재 role로 발급
  5. 로그아웃: 예외 없이(멱등) Redis 삭제 + 두 쿠키 Max-Age=0. 기존에는 쿠키가 남고, Redis에 토큰이 없으면 400
- 택하지 않은 대안: rotation 없이 access만 재발급(refresh token 탈취 시 7일간 무제한 재발급), refresh token을 바디로 받기(JS에서 읽을 수 있어 XSS에 노출)
